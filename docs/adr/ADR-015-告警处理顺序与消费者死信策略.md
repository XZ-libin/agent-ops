# ADR-015：告警请求处理顺序修订与消费者死信策略

- 状态：已接受
- 日期：2026-10-13（第十六轮）
- 决策者：业务方裁决（本轮裁决 1–3）
- 关系：**不修改 ADR-001 至 ADR-013**；ADR-014 的其余条款保持有效，
  本 ADR 仅修订其 §3 的请求处理顺序并新增消费者死信策略

## 背景

第十五轮落地告警入口后，评审指出两处问题：

1. **处理顺序**：ADR-014 把限流放在源白名单**之前**（理由是防止随机 source 绕过限流），
   但这会让未授权 source 也占用限流桶；而桶表没有淘汰策略，可能被撑爆。
2. **消费者无重试上限**：失败事件保持 pending、没有次数上限，可能无限重试，
   也没有死信出口。

## 决策

### 1. 请求处理顺序（修订 ADR-014 §3）

新顺序（固定，不可调换）：

```
① 读取请求体（上限 64KB → 413）
② 解析 JSON（失败 → 400）
③ 源白名单检查（不在白名单 → 403；不做签名校验、不分配桶、不写任何表）
④ 签名校验（使用该源密钥；失败 → 401；不消耗令牌）
⑤ 每源限流（令牌不足 → 429 + Retry-After；桶已按白名单预分配）
⑥ 字段校验（severity 白名单、必填字段 → 400）
⑦ 去重 upsert → 写 test_alerts 与 test_outbox
```

关键性质：

- **白名单最先**：不在白名单中的 source 直接 403，**不分配任何桶**；
  白名单是有限集合，因此桶表有上限；
- **签名之后才限流**：只有签名校验通过的请求才消耗令牌。伪造签名的请求
  只消耗 HMAC 的 CPU，**不能耗尽某个合法源的配额**——攻击者无法通过
  伪造请求让合法源被限流；
- 代价：伪造请求仍会读取最多 64KB 请求体并计算 HMAC；
  这一点由反向代理的**全局限流**处理，留到部署阶段（见 TODO）。

### 2. 桶表有界（关闭 ADR-014 的"桶表无淘汰"TODO）

- 每个白名单源在**启动时预分配**桶（`NewLimiterForSources`）；
- 桶表键数 == 去重后的白名单长度，**运行期间不新增键**；
- 未预分配的 source 不会被分配桶（`Allow` 返回 `known=false`，
  调用方本应先经白名单拒绝；出现 `known=false` 视为配置不一致 → fail-closed 403）；
- 因此**不需要淘汰策略**：桶表大小在启动时即确定。

### 3. 消费者重试与死信（新增，ADR-014 §5 未覆盖）

- outbox 事件记录 `attempts` 计数；
- 失败后按**退避**再次尝试（经注入时钟控制）：第 1 次失败后 1s、第 2 次 2s、
  第 3 次 4s、第 4 次 8s；
- **第 5 次（MaxAttempts）失败后**：状态置 `dead`，**不再自动重试**；
- 退避时间未到时事件不会被选中（查询条件含 `next_attempt_at <= now`）；
- **死信数据保留、不删除**；人工重新投递命令本轮不实现（见 TODO）；
- 单条事件失败**不中断整批**：本批继续处理其余事件；
- 失败原因不落库（避免把外部错误原文写入存储）。

## 影响

- `alerts/internal/ingest/ratelimit.go`：新增 `NewLimiterForSources`（预分配）、
  `BucketCount`，`Allow` 返回三值 `(allowed, retryAfter, known)`；
- `alerts/internal/httpapi/server.go`：处理顺序按本 ADR 调整；
- `alerts/internal/store/store.go`：outbox 新增 `attempts`、`next_attempt_at`，
  `status` CHECK 扩展为 `pending|consumed|dead`；
- `alerts/internal/consumer/consumer.go`：新增 `MaxAttempts`、`Backoff`、
  `recordFailure`、`Attempts`、`Status`、`DeadCount`；
- ADR-014 的其余决策（fingerprint 主键 upsert、源白名单与每源密钥、64KB、
  severity 白名单、表名守卫、每轮 schema、不做诊断）继续有效。
