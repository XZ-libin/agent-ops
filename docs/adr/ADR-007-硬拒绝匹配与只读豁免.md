# ADR-007：硬拒绝规则匹配语义与只读豁免

- 日期：2026-10-12
- 状态：Accepted
- 上游：开发文档 v2「范围与非目标」「风险策略与审批」、ADR-006

## 背景

ADR-006 确定了硬拒绝规则为第二道防线（能力即使被误声明也不执行），但没有定义"命中"的匹配语义；同时，上下文升级规则未明确只读能力是否豁免——若只读诊断在生产环境或冻结窗口内也被升级，排障将无法进行。

## 决策

1. **硬拒绝规则匹配语义**：
   - 删除类操作（规则名以 `delete` 结尾，如 `volume.delete`、`database.delete`）一律按**前缀匹配**。若采用精确匹配，删除能力只需改名为 `volume.delete_all`、`volume.delete.snapshot` 等变体即可绕过硬拒绝；前缀匹配保证删除操作的任何变体都命中。
   - 以 `.` 结尾的规则（`firewall.`、`security_group.`）按前缀匹配（覆盖其命名空间下的所有操作变体）。
   - 其余规则（`audit.disable`）为精确匹配。
2. **只读豁免**：`read_only` 等级不受环境（生产）、影响范围（multi）、可逆性与冻结窗口等写操作上下文因素升级，直接按基础等级参与等级→决策映射（默认映射为 auto）。

## 后果

- 硬拒绝无法通过改名绕过；策略引擎的判定理由会记录命中的规则原文，便于审计复核。
- 只读排查在生产环境与冻结期内不受限制，诊断可用性得到保证。
- 新增能力命名时应避免与禁止前缀冲突（契约评审时检查），否则会被硬拒绝兜底拦截。

## 相关测试

- control-plane/internal/policy：
  - `TestHardDenyRenameBypass`（volume.delete_all、volume.delete.snapshot、database.delete_drop、firewall.rule_add、security_group.rule_add 五个改名变体均 deny 并断言命中规则）；
  - `TestReadOnlyNoUpgradeProdFreezeMulti`（read_only 在 prod + 冻结窗口 + multi 影响范围下仍为 auto）；
  - `TestHardDenyMisdeclared`、`TestHardDenyExactMatch`。

## 修订记录

- 2026-10-12（修订 1）：硬拒绝判定改为「destructive 标注 + 名称前缀」双重防线。
  1. **删除"以 `delete` 结尾"的名称后缀判据**：不再通过能力名称推断删除类——`volume.remove`、`volume.destroy`、`volume.wipe` 等改名后不带关键词即会漏判，名称推断不可靠。
  2. **第一道防线改为能力清单的 `destructive` 标注**：契约（proto `Capability.destructive`，默认 false）显式声明"不可逆或删除语义"，策略引擎对该类能力一律 deny（理由："能力标记为破坏性，硬拒绝"）。
  3. **名称规则保留为第二道防线**，并统一为前缀匹配：比较前对规则名归一化（去掉末尾 `.`），不再区分 `.` 结尾与否。
  4. 实现状态：destructive 字段的 proto 契约变更**待确认后落地**（见本轮报告）；名称前缀防线已生效。

- 2026-10-12（修订 2）：名称校验、前缀误伤取舍与幂等超时语义。
  1. **能力名称校验（fail-closed）**：名称必须满足 `^[a-z0-9_]+(\.[a-z0-9_]+)*$`（规则实现于 internal/registry，注册处与策略评估处两处强制）。不合法一律 deny，理由"能力名称不合法"；**不做自动修正**（不把 `Volume.Delete` 转成 `volume.delete` 后放行）——修复大小写绕过。
  2. **名称前缀规则保持小写字符串前缀，不改为分段匹配**：字符串前缀会误伤（如 `firewall` 命中 `firewallctl`），这是**有意的 fail-closed 取舍**。
  3. **幂等处理中超时（abandoned 语义）**：处理超过 `lease_until` 后状态转为 abandoned；同 key 返回 409（ErrAbandoned），响应说明"上一次操作状态未知，已放弃，请使用新的 key 重试"；**绝不同 key 重新执行**（原操作可能仍在运行，由操作者换新 key 重试）。过期与租约判定统一使用注入时钟，不使用数据库 `now()`。

- 2026-10-12（修订 3）：destructive 字段落地（proto 字段 7，已批准执行）。
  1. `Capability.destructive`（默认 false）正式进入契约，策略引擎对其一律 deny，理由固定为"能力标记为破坏性，硬拒绝"。
  2. **破坏性能力的执行路径永久排除在 Agent 之外**（策略层 deny 保证）：Agent 不会执行 destructive 能力；**人工执行通道是另一套设计，本期不做**。
